# Database migrations runbook

Schema is managed by Alembic (`backend/migrations/`). The app does **not** create or
alter tables on startup — every schema change is a migration that must be applied with
`alembic upgrade head`.

All commands below run from `backend/`. Substitute the interpreter for your environment
(`.venv/bin/python` on Linux/macOS, `.venv/Scripts/python.exe` on Windows). On a server,
export the real `DATABASE_URL` first so Alembic touches the deployed database and not the
default `backend/app.db`:

```bash
set -a; . ../.env; set +a
```

Alembic reads the URL from `app.database` (`DATABASE_URL` env var, else `sqlite:///app.db`),
so `alembic.ini` needs no editing.

## Normal workflow (after changing `models.py`)

```bash
.venv/bin/alembic revision --autogenerate -m "describe the change"   # generate
# review the generated file in migrations/versions/ before committing
.venv/bin/alembic upgrade head                                       # apply locally
.venv/bin/alembic check                                              # expect: "No new upgrade operations detected"
```

Alembic autogenerate does not catch everything on SQLite (notably column *type* changes
and some constraint edits) — always read the generated migration and fix it by hand where
needed.

## Adopting a database that predates Alembic

A database created before Alembic was introduced (2026-08-30) has all its tables but no
`alembic_version` row. Running `alembic upgrade head` against it would try to `CREATE TABLE`
objects that already exist and fail. Bridge it once:

```bash
set -a; . ../.env; set +a
.venv/bin/python -m alembic current          # prints nothing  -> untracked, continue
.venv/bin/python scripts/bootstrap_alembic.py  # detects the pre-Alembic DB, stamps it at 0001
.venv/bin/python -m alembic upgrade head        # applies 0002+ for real
.venv/bin/python -m alembic check               # verify the schema now matches models.py
```

`scripts/bootstrap_alembic.py` is safe to run every time:

- already-tracked database -> no-op
- brand-new empty database -> no-op (the baseline migration creates the tables)
- pre-Alembic database -> `alembic stamp 0001`

`alembic stamp` only writes the version row; it runs no SQL and **asserts** the live schema
already matches revision `0001`. If the pre-Alembic schema had drifted from the baseline
(e.g. an old `Base.metadata.create_all` added a column the baseline doesn't have), that
drift is now invisible to the version row — which is what the `alembic check` step catches.

### If `upgrade head` fails with "table/column already exists"

The pre-Alembic schema was ahead of the baseline. Stamp past the migration whose objects
already exist, then reconcile:

```bash
.venv/bin/python -m alembic stamp <that-revision>
.venv/bin/python -m alembic check       # lists what is genuinely still missing
```

Add only the missing pieces — either a hand-written migration for the diff, or a manual
`ALTER TABLE` followed by another `alembic stamp` — then re-run `alembic check` until clean.

## Troubleshooting: `sqlite3.OperationalError: no such column: ...`

The running code expects a column a migration adds, but that migration was never applied to
this database. Cause is almost always one of:

1. The deploy did not run `alembic upgrade head` (see below).
2. The database predates Alembic and was never adopted — follow *Adopting a database that
   predates Alembic*.
3. `alembic_version` is stale (points at a revision id that no longer exists, e.g. an
   autogenerated hash that was later renamed) — `alembic current` errors. Fix with
   `alembic stamp <baseline>` then `alembic upgrade head`.

## Deployments must run migrations

`deploy.sh` applies migrations in step 3/8:

```bash
"$APP_DIR/.venv/bin/python" scripts/bootstrap_alembic.py
"$APP_DIR/.venv/bin/python" -m alembic upgrade head
```

If deployment is driven by a wrapper command on the server rather than `deploy.sh`
directly, that wrapper must either delegate to `deploy.sh` or run those same two lines
before restarting the service. A deploy that skips them will restart the app against an
out-of-date schema and every request touching the new column 500s.
